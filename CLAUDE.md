# Working on Nimbus

Nimbus is a from-scratch, offline cloud emulator in Go with a live web visualizer. Azure and AWS run on the same core; GCP comes later. The owner is learning cloud engineering through it: explain non-obvious protocol details in comments, keep the code readable.

## Ground rules

- **Main module is stdlib-only.** No third-party Go deps in `github.com/Asere231/nimbus`. Test harnesses that need SDKs live in their own module under `test/`.
- **The visualizer has no build step and no CDN.** Plain HTML/CSS/JS in `internal/ui/static`, embedded with `go:embed`. It must work offline.
- **Real clients are the spec.** Match what the azurerm provider / `hashicorp/go-azure-sdk` actually send and expect, not what the docs say. When unsure, read the SDK source (shallow-clone `github.com/hashicorp/go-azure-sdk`, look in `sdk/client/resourcemanager` and `sdk/environments`).
- **Never call real cloud endpoints.** DNS suffixes in the metadata stay on `*.nimbus.localhost`.
- Run `gofmt -l .`, `go vet ./...`, `go test ./...` before finishing any change.

## How a request flows (Azure)

1. `internal/azure/server.go` `ServeHTTP` routes metadata, token, OpenID, async-operation paths, else ARM.
2. `internal/azure/ids.go` `parseTarget` turns an ARM path into a `target` (kind, type, ID, parent).
3. `internal/azure/arm.go` handles it generically: PUT/PATCH/GET/HEAD/DELETE, lists, actions.
4. Per-type behaviour lives in **hooks** (`Hook{BeforePut, AfterPut, AfterDelete, Backing}`), registered in files like `network.go`.
5. `internal/core/store.go` stores the ARM JSON and publishes events; `internal/ui` streams them to the browser.

## Protocol facts already learned (do not regress)

- Metadata (`/metadata/endpoints?api-version=2022-09-01`) is a **single JSON object**, not an array. `name`, `resourceManager` and `microsoftGraphResourceId` are required.
- `resourceManager` must have **no trailing slash**; the SDK joins `base + "/" + path`, and a `//` makes its pollers compute the wrong resource path (delete polling never ends).
- Writes return `Azure-AsyncOperation` + `Retry-After: 1`; the operation URL always says `Succeeded`. Without it the SDK waits 10 s per resource. Older SDK versions always use the 10 s delete poller for DELETE.
- Responses must be `Content-Type: application/json` or the SDK skips provisioning-state checks.
- Deleting something absent returns 204. A missing resource group is `ResourceGroupNotFound`; other misses are `ResourceNotFound`.
- Tokens are unsigned JWTs; clients only decode the claims (`oid`, `tid`, `appid`).
- A resource's `id` and `name` are fixed when it is created. ARM resolves IDs case-insensitively but always answers with the casing used at creation, and the name is immutable. Take them from the path only on create, or a client using different casing silently renames the resource and Terraform sees a perpetual diff.
- **macOS rejects long-lived server certificates** with `x509: "localhost" certificate is not standards compliant`, which never mentions dates. The limit is on the validity *span* (`NotAfter - NotBefore`): measured on macOS 27, 824 days passes and 825 fails. Backdating `NotBefore` for clock skew spends part of that budget. Compute `NotAfter` from `NotBefore` as a plain duration in UTC — `AddDate` works in the local zone, so crossing a daylight-saving boundary shifts the span by an hour. Nimbus uses 397 days, under Apple's documented 398.
- **Nested `*.localhost` names resolve to loopback on macOS and Windows, with nothing installed.** `st1.blob.storage.nimbus.localhost` returns `127.0.0.1`/`::1` with no `/etc/hosts` entry, no `/etc/resolver`, and no hosts-file edit on Windows — verified on macOS 27 (system resolver, and Go's with both the cgo and pure-Go resolvers) and on Windows via `[System.Net.Dns]::GetHostAddresses`, which is the `getaddrinfo` path the SDKs use. So the storage data plane needs no DNS tooling. Do not build `nimbus dns`.
- **The storage data-plane suffix carries our port**, which real Azure's never does. azurerm builds data-plane URLs as `https://%s.blob.%s/` from `suffixes.storage` (NOT from `primaryEndpoints`), so a bare hostname would send it to port 443, which needs root to bind. `storage.nimbus.localhost:4701` substitutes into that format string as a valid URL on our own port, and SNI still sees the bare hostname so the certificate matches.
- **A few types' create must answer 202, not 201.** Their SDK clients are generated as long-running and reject anything else outright: `performing Create: unexpected status 201 (201 Created)`. Storage accounts are the first; network types still expect 201. `Hook.CreateStatus` is how a type opts in.
- **A TLS wildcard matches exactly one label.** `*.localhost` does not cover `a.b.localhost`, so each storage service level needs its own SAN (`*.blob.storage.nimbus.localhost`, `*.queue.…`). Adding a name to `serverDNSNames` reissues certificates that predate it, reusing the CA so no re-trust.
- **azurerm polls the blob service for data-plane readiness** right after creating an account (`GET /?comp=properties&restype=service`), and fails the apply if it does not answer. The account cannot finish applying without a working blob endpoint.
- **The Table service signs differently from blob and queue.** A shorter header list, `x-ms-date` instead of `Date`, no `x-ms-*` block at all, and a canonicalised resource carrying only the `comp` parameter. Reading `Date` gives an empty field and a 403 that explains nothing.
- **`Content-MD5` is a content setting, not an automatic property.** A blob uploaded without `x-ms-blob-content-md5` has none; do not compute one. azurerm stores whatever is returned on first read, after which the config (silent about `content_md5`) disagrees with state and every plan wants to replace the blob, since `content_md5` is ForceNew.
- **azurerm 4.x creates containers through ARM** when `azurerm_storage_container` is given `storage_account_id`, but `azurerm_storage_blob`, `az` and every SDK use the data plane. A container made one way must exist the other, or an apply fails with `ContainerNotFound` on a container Terraform created seconds earlier. Both directions are mirrored in `storage.go`.
- **Metadata names must come back lower-cased and written verbatim.** Clients compare them literally — the Python SDK strips `x-ms-meta-` and uses the rest as a dictionary key, so `X-Ms-Meta-Owner` yields `Owner` and a lookup of `owner` misses. Go canonicalises header names on *both* sides, so the read path lower-cases and the write path assigns into `w.Header()` directly instead of calling `Set`.
- **A few types' create is long-running for real**, and the operation endpoint has to track state (`internal/azure/operations.go`). An unknown operation ID 404s, as ARM does — measured: azurerm does NOT mistake that for success. Restarting Nimbus mid-apply still fails the apply with `unimplemented polling status "Unknown"`, but that is the poll hitting a **closed port**, not the operation being lost; nothing we return can improve it.
- **`identityProfile.kubeletidentity.resourceId` must be a full UserAssignedIdentity ARM ID**, not a name. A name fails the apply with `parsing the UserAssignedIdentity ID: the number of segments didn't match`, naming neither the field nor the resource. Azure puts it in the node resource group as `{cluster}-agentpool`.
- **azurerm scales a node pool by PUTting the `agentPools` CHILD**, then reads the count back off the **parent** cluster's `agentPoolProfiles` on the next refresh. Without mirroring child into parent, the apply reports success, no node appears, and the plan is dirty forever. Same parent/child sync the VNet and its subnets need — treat it as a shape, not a one-off.
- **Anything azurerm re-reads must be derived, not generated.** The AKS kubeconfig, `fqdn`, `nodeResourceGroup` and identity GUIDs are hashes of the resource ID or built once and returned byte-for-byte. A value that differs between reads is a permanent diff; this is the `Content-MD5` lesson generalised.
- **A Key Vault's data-plane address comes from `properties.vaultUri`**, which azurerm reads through ARM ("looking up base uri for secret %q in %s") and then uses for every secret call. The metadata `keyVaultDns` suffix carries our port too, for the `az` CLI, which never reads the metadata document.
- **The Key Vault `401` challenge's `authorization` URL must carry a tenant path segment.** go-autorest, still used by the provider for Key Vault, parses the challenge with `bc.values[tenantID] = asURL.Path[1:]`, so a bare origin panics it: `slice bounds out of range [1:0]`, with nothing in the trace mentioning Key Vault. Send `authorization`, `authorization_uri`, `resource` and `scope`, and give the authority a tenant.
- **Reading a vault through ARM makes azurerm read CERTIFICATE CONTACTS from the data plane.** Returning 501 there crashes its Key Vault client. Real Key Vault answers `404 ContactsNotFound` when none are set, which azurerm tolerates deliberately — so answer that.
- **Purging a vault is long-running** (202 + `Azure-AsyncOperation`). A plain 200 sends the poller to the deleted-vault URL, where our own 404 reads as a failed purge and fails the destroy.
- **Deleting a user-assigned identity is synchronous** (200). A 202 fails with `unexpected status 202 (202 Accepted) received with no body`, like storage account and container deletes.
- **azurerm maps a vault URI back to a resource ID through `/subscriptions/{id}/resources`** with a `resourceType eq '...'` filter, not through anything Key Vault-shaped. Without that path the destroy fails while "populating the Key Vaults cache".
- **RBAC is recorded, never enforced.** Role assignments and the built-in role definitions round-trip (with the real GUIDs), but no request is ever refused for lacking a role. A local apply therefore cannot prove a deployment's permissions are right.
- **ACR's `loginServer` is `localhost:<port>`.** Docker treats a registry on localhost as insecure by default, so `docker push` needs no daemon configuration — verified through Docker Desktop's VM on macOS. A pretty hostname would need TLS the daemon trusts (its trust store is inside that VM) or an insecure-registries edit.
- **k3s v1.34.12 points containerd at `certs.d`** (`config_path` in its generated `config.toml`), so a mirror written to `.../certs.d/<host>/hosts.toml` takes effect on the next pull with no restart — which is what lets a registry created *after* a cluster still be pullable. The registry container must also join the cluster's Docker network to be resolvable by name. `registries.yaml` is written as well, for builds that only read registry configuration at startup.
- **Soft-deleted vaults are not persisted** across a restart, like operations: a name that was taken becomes free again. The harmless direction to diverge in.

- **Get-then-Put is a lost update, even though it re-reads.** Mirroring a child into its parent, recording an endpoint from a background `Provision`, moving a provisioning state along — each one reads the body, changes it and writes it back, which looks safe and is not: two that overlap both read the same copy and the second to write restores the first one's change. Measured, not theorised: scaling an AKS node pool lost the new count on a loaded CI runner while passing fifty times in a row locally, because the pool's `AfterPut` and the cluster's `Provision` were writing the same body. **Use `core.Store.Update`**, which holds the store's lock across read, change and write. Every parent/child mirror must go through it.
- **The event journal only ever hears about CHANGES, and a restart is not one.** Everything loaded from `state.json` is simply there, unannounced — and `ensureSubscription` skips its `Put` when the subscription already exists, so even that publishes nothing. A replay of the next run then starts from an empty world and shows only what that run touched, floating with no resource group around it. Startup writes a `kind: "snapshot"` record per resource straight to the journal (never through the bus, or every restart would fill the activity feed with things that did not happen). Snapshots take no part in run grouping: one that started a run would be excluded from that run's own baseline, which is the thing it was written for.
- **Windows's clock is coarse — a millisecond or worse — and two things written back to back share a timestamp.** A startup snapshot and the first event of the apply that follows it land in the same tick, so anything comparing them with a strict `Before` silently drops one. A snapshot is a statement about what already existed rather than something that happened at an instant, so it counts as "at or before" the run it precedes; an ordinary event at that instant belongs to the run. macOS and Linux never show this; the Windows CI leg does, which is what it is for.
- **A `core.Event` is enough to draw a resource**: it carries the id, type, name and parent of whatever changed. That is what makes replay possible without snapshots — including for a resource that has since been destroyed and cannot be looked up. Do not slim the event down.
- **The request that caused a change is logged AFTER it.** `store.Put` publishes the resource event in the middle of handling the request, and `ServeHTTP` publishes the request event once it has a status and a duration. Looking backwards for "the call that did this" finds the previous, unrelated one.
- **Within one millisecond, order must come from the array, not the timestamps.** azurerm PUTs independent resources concurrently, so three creates share a millisecond; a JavaScript `Date` keeps only milliseconds and compares them equal. The server sorts with nanosecond precision, so the order it sent is the answer.
- **azurerm's resource-group create is silent for ~20 seconds.** Not polling, not re-reading: nothing on the wire at all. It is the longest gap inside any apply we make, which is why the run-grouping threshold is 30 s (`core.RunGap`) and not something smaller.
- **A resource about to be created has no ID in a Terraform plan.** `terraform show -json` lists `id` under `after_unknown` for a create, because the provider has not been called yet; `after.name`, `after.location` and `after.resource_group_name` ARE there. Updates and deletes carry `before.id`. Anything matching plan entries to resources has to handle the two cases separately. Six of eight entries in a real plan are `no-op`, and a replace arrives as two actions in one entry, in either order.
- **Kubernetes' `spec.selector` is two different shapes.** A Service's is a plain map of labels; a Deployment's or ReplicaSet's is a LabelSelector with them under `matchLabels`. One Go type for both decodes the other into nothing, silently — and with no selector, no pod is drawn behind its service.
- **An external stylesheet does not apply to a detached SVG.** An exported graph, or one rendered inside `<img src="data:image/svg+xml,...">`, gets none of `style.css`: it has to carry its own `<style>`, or it comes out as unstyled black text on nothing. The same applies to the canvas path behind PNG export.
- **The visualizer is ES modules with no build step**, so nothing resolves an import until a browser does: a typo in a module path is a blank page at runtime and nothing at compile time. `TestEveryModuleImportResolves` walks the import graph from `index.html` outwards for exactly that reason. The static files are embedded by `//go:embed static`, so **a change to anything under `internal/ui/static` needs a rebuild before it reaches the browser** — and tests must not live in there, or they ship to users. They are in `test/ui`, run by `node --test`.
- **`az deployment` does not send JSON.** It serialises the request, chops the closing braces off and splices the template back in under an *unquoted* key: `partial_request[:-2] + ", template:" + template + "}}"` (azure-cli `resource/custom.py`), calling it "a JSONC format that service can deserialize". `encoding/json` rejects it with `invalid character 't' looking for beginning of object key string`, and `--debug` shows valid JSON because az logs the body *before* rewriting it — its own source calls this "a very difficult-to-debug issue". `quoteBareKeys` in `jsonc.go` repairs bare keys, but only after a strict parse has already failed.
- **A parameter's `defaultValue` is usually an expression**, `[resourceGroup().location]` above all, and has to be evaluated like anything else; defaults can refer to other parameters, so they settle iteratively. Taking them literally leaves the expression in the resource body. The deploy path hides this by evaluating the body a second time, so the symptom appears only in what-if: `Modify` for resources nothing has touched.
- **A fresh server must already list its subscription.** `az login` lists subscriptions first; finding none it makes a tenant-level account and then uses the TENANT id as the subscription id, so everything lands under the wrong one. Terraform never notices, because it is always given an explicit `subscription_id`.
- **Compiled Bicep passes an api-version to `reference()`** as a second argument (`reference(resourceId(...), '2023-09-01')`), where hand-written ARM usually passes nothing or `'Full'`. Treat any non-`Full` second argument as the api-version and ignore it.
- **`az` compiles Bicep on your machine**, so Nimbus never sees a `.bicep` file and needs no Bicep parser. `az deployment group create --template-file x.bicep` shells out to `bicep build --stdout` before its first HTTP call (measured in az 2.90.0, `command_modules/resource/custom.py`). Templates arrive as ordinary ARM JSON.
- **A Bicep `for` inside a property is NOT a resource copy.** It compiles to a property-level copy — an object carrying `{"copy":[{"name","count","input"}]}` that expands into a sibling array — which looks nothing like the resource-level copy that repeats a whole resource. A template engine that implements only the latter silently produces a resource with no subnets.
- **`validate` and `whatIf` are POSTed at a deployment name that does not exist yet**, which is the entire point of them, so they have to be answered before the usual "does this resource exist" check.
- **`uniqueString()` is not reproducible from outside Azure**: the algorithm is unpublished. Nimbus returns a deterministic 13-character value that is stable and unique but differs from Azure's. Templates that only need a unique repeatable name are unaffected; one that compares against a value computed in real Azure is not.
- **Etags are derived from the resource ID, not generated.** Azure changes an etag on every write; doing the same here made redeploying an unchanged template rewrite the resource. Nothing Nimbus serves does optimistic concurrency, so there is nothing to lose and a stable read to gain. Same rule as the AKS kubeconfig and `Content-MD5`.
- **When reading Microsoft's OpenAPI specs, every property must keep the file it was declared in.** A resource's `allOf` almost always reaches into `common-types`; if that file becomes "the" current document, the resource's own `$ref`s resolve against it, find nothing, and the type yields zero fields **with no error at all**. `tools/specgen` pins this with a test, and reports unresolvable refs rather than swallowing them.
- **`az cloud register` reads `/metadata/endpoints` at once**, so the Nimbus CA has to be trusted *before* that command runs, not before the first `az keyvault` call. It fails with an SSL error that blames the network. So the metadata document is not only a Terraform/SDK mechanism after all — az fetches it too. `nimbus az register --run` sets `REQUESTS_CA_BUNDLE` on each child process rather than relying on the shell.
- **MSAL validates an unknown authority against the real `login.microsoftonline.com`** before it will talk to ours, which both reaches the internet and then fails, because `REQUESTS_CA_BUNDLE` has replaced the system trust store and a genuine Microsoft certificate no longer verifies. The error says "behind a proxy" and names no authority. `az config set core.instance_discovery=false` turns it off — the switch Azure Stack uses (`azure/cli/core/_profile.py`). An `/adfs`-suffixed authority also disables it, but rewrites the tenant to `adfs`.
- **`az cloud register` is not idempotent** (`The cloud 'nimbus' is already registered`), which re-registering after a port change always hits. The same flags work as `az cloud update`.

- **Some azurerm delays cannot be fixed from this side.** A resource group takes ~20 s to create and every DELETE a flat 10 s, no matter what we return. `azurerm_resource_group` ignores `Azure-AsyncOperation` and runs its own client-side wait that re-reads the group several times; the delete poller waits, then GETs until the resource 404s. Adding async headers to resource-group writes or `Content-Type` to the empty 202 changes neither. Measured against azurerm 4.81.0 — don't re-chase it.

## AWS protocol facts (measured against aws-cli 1.40.33 / botocore 1.38.34)

- **The URL says nothing; the signature is the routing table.** Every Query service POSTs to exactly `/` with `Action=X&Version=Y` form-encoded. STS, EC2 and IAM differ only in the fourth field of the SigV4 credential scope (`Credential=nimbus/20261106/us-east-1/sts/aws4_request`) and in the Action. So `internal/aws/sigv4.go` routes on the credential scope, falling back to `X-Amz-Credential` for presigned URLs and to S3 for an unsigned request. Signatures are never verified — a local emulator rejecting one could only ever be reporting a clock skew.
- **There are three error envelopes and they are different documents.** IAM/STS use `<ErrorResponse><Error><Type><Code><Message></Error><RequestId>`; EC2 uses `<Response><Errors><Error>…</Errors><RequestID>` — note `RequestID`, not `RequestId`; S3 uses a bare `<Error>` with `<Resource>`. A client handed the wrong one prints `An error occurred (Unknown) when calling the … operation`, naming nothing.
- **A 5xx is retried five times** with backoff, so an action that will never work must answer **400**, not 501: one legible line instead of five, and no hammering. Nimbus answers `InvalidAction` naming the service and action, which also makes the activity feed the to-do list for the next checkpoint.
- **The XML namespace is part of the contract.** It is per service and per version (`https://sts.amazonaws.com/doc/2011-06-15/`); a client parsing with the wrong one sees an empty document rather than an error.
- **AWS ids are decided once at create and stored, never recomputed.** This looks like the "derive, do not generate" rule but is not: that rule is about values a client COMPARES between reads, and a stored id agrees with itself. Deriving a VPC id from its inputs would merge two VPCs that happen to share a CIDR.
- **A VPC's attributes are read one call at a time, and there are more than you think.** After creating a VPC, aws provider 5.100.0 calls `DescribeVpcAttribute` three times: `enableDnsSupport`, `enableDnsHostnames` and `enableNetworkAddressUsageMetrics`. A 400 on any one fails the whole apply, and the list grows with provider versions, so an unmodelled attribute answers `false` rather than refusing. Note also that `ModifyVpcAttribute` capitalises the name (`EnableDnsSupport.Value`) while `DescribeVpcAttribute` does not.
- **A security group rule with protocol `-1` must be compared without its ports.** The provider revokes the default egress rule with `FromPort=0&ToPort=0&IpProtocol=-1`, while `DescribeSecurityGroups` reports that same rule with no ports at all. Compare them strictly and the revoke never matches, so every `aws_security_group` with its own egress rules fails to create with `InvalidPermission.NotFound`.
- **The provider also revokes an IPv6 `::/0` egress rule that AWS only creates in an IPv6-enabled VPC.** Against a v4-only VPC that second revoke fails with `InvalidPermission.NotFound` on real AWS too, and Terraform carries on. The red line in the activity feed is accurate; do not invent a `::/0` rule to silence it.
- **A describe for a specific id must ERROR when it is missing, not return an empty list**, and with that kind's own code (`InvalidVpcID.NotFound`, `InvalidSubnetID.NotFound`, …). The provider matches on the code to tell "already gone" from "something is wrong"; the wrong one makes a destroy retry until it times out.
- **An unknown describe FILTER must be ignored, not refused.** The provider sends filters nobody has implemented; ignoring one can only ever return too much, which the client narrows itself, while an error fails an apply for no reason.
- **`encoding/xml` appends to a slice that is already populated** rather than replacing it. Reusing one decode target across two responses silently accumulates them — which is how this project's first EC2 tests reported three tags where there were two.
- **A bucket's configuration is a dozen separate documents, and the provider reads EVERY one after creating it.** `?tagging`, `?policy`, `?cors`, `?website`, `?lifecycle`, `?replication`, `?publicAccessBlock`, `?encryption`, `?ownershipControls`, `?object-lock` must each answer **404 with that sub-resource's own code** when unset (`NoSuchTagSet`, `NoSuchBucketPolicy`, `ServerSideEncryptionConfigurationNotFoundError`, …) — the provider is written to tolerate exactly those. `?versioning`, `?acl`, `?location`, `?requestPayment`, `?accelerate`, `?logging` and `?notification` are never errors and answer with an empty or default document. This is Milestone 4's Key Vault certificate-contacts lesson, one service later and ten times over.
- **`?location` reports us-east-1 as an EMPTY `LocationConstraint`.** S3's oldest wart, and still how every client reads it.
- **A bucket policy is JSON, not XML** — the one S3 call that is — and must come back byte for byte.
- **S3 refuses to delete a bucket that is not empty** (`BucketNotEmpty`, 409) and the provider depends on it: `force_destroy` works by emptying the bucket first. A silent cascade would quietly destroy a bucket it meant to keep. Deleting an OBJECT that is not there, by contrast, succeeds — that is what makes a destroy idempotent.
- **An S3 key is not a path.** `../../etc/passwd` is a legal key that S3 stores flat and meaninglessly; written through `filepath.Join` it leaves the data directory. `cleanKey` refuses it.
- **Object metadata repeats the Azure blob trap**: `x-amz-meta-*` names must come back lower-cased and be written into the header map directly, because Go canonicalises header names on both sides and a client looks the key up literally.
- **IAM's XML differs from EC2's twice over**, though both are Query: lists are wrapped in `<member>` rather than `<item>`, and results sit one level deeper inside `<XxxResult>`. IAM also tags with `Tags.member.N.Key` where EC2 uses `Tag.N.Key`.
- **IAM returns policy documents URL-ENCODED** and the SDKs unescape whatever comes back. Raw JSON works right up until a document contains a `+` or a `%`, after which the client quietly reads different text than was stored — a diff that never settles with nothing to point at.
- **IAM has ONE not-found code, `NoSuchEntity`,** for every kind — unlike EC2, which has a different one per kind.
- **A create that succeeds but whose RESPONSE fails to parse leaves an orphan.** A malformed `CreateRole` reply (mine closed `<Role>` with `</iamRole>`) still created the role; the retry then hit `EntityAlreadyExists` with nothing in Terraform state to explain it. When a create appears to fail, check the store before assuming nothing happened.
- **A container that outlived the store must be adopted on the port it already publishes.** `Start` reuses a running container it finds by name — the case after a restart without `--persist` — but it had already asked `FreePort` for a port, and the old port is taken by that very container, so it got a different one. The readiness probe then waited out the whole timeout against a closed port and reported a healthy cluster as FAILED. Measured: `terraform apply` sat in CREATING for four minutes and then failed with `unexpected state 'FAILED'`.
- **Every `public.ecr.aws/lambda/<runtime>` image ships the Runtime Interface Emulator**, so a handler runs in Nimbus on the same runtime interface client that runs it in production — no handler protocol to implement. RIE listens on 8080 and the invocation path is `POST /2015-03-31/functions/function/invocations`, where the literal `function` is RIE's own and NOT the function's name.
- **RIE's port opens before the handler is loaded**, so a successful TCP connection proves nothing: readiness has to be a real invocation, or the first genuine one fails with a connection reset that looks like the handler's fault.
- **RIE prints its own START/END/REPORT trio and its REPORT always says `Memory Size: 3008 MB`**, whatever the function was configured with, because it does not implement memory limits. It also logs its internals with a `(rapid)` tag, which real Lambda never shows. Passing that through put every invocation in the log group twice, once with the wrong memory size — so the emulator's bookkeeping is dropped and Nimbus's own lines, carrying the request id the client was given, are kept.
- **`AWS_ENDPOINT_URL` is all it takes for a handler to reach Nimbus.** Every current SDK reads it, so a function written against real AWS — `boto3.client("dynamodb")`, no endpoint in the code — talks to Nimbus unchanged. It must name `host.docker.internal`, because inside the container localhost is the container. Measured end to end: a Python handler wrote an item that `aws dynamodb scan` then returned.
- **A zip entry is a NAME, not a path.** `../../etc/passwd` is a legal entry and `filepath.Join` happily writes it outside the function's directory — the S3 key trap again, refused the same way. The executable bit has to survive unpacking too, or a custom runtime's `bootstrap` fails with `exec format error`.
- **Whether a handler threw is a HEADER**, `X-Amz-Function-Error: Unhandled`, not a shape in the body: the body is whatever the handler returned, byte for byte. `aws lambda invoke` prints `FunctionError` from that header alone.
- **Lambda's paths are versioned per operation, not per service**: `/2015-03-31/functions/...`, tags under `/2017-03-31/tags/{arn}` with the ARN URL-encoded into ONE path segment (colons and all), code signing under `/2020-06-30/`. Create answers **201**, delete **204 with no body**, and `GetPolicy` with no policy must be `ResourceNotFoundException` — the one the provider tolerates, exactly like Key Vault's certificate contacts.
- **CloudWatch Logs is JSON 1.1 and spells its fields in lowerCamelCase** (`logGroupName`), where DynamoDB — JSON 1.0 behind the same port — uses TitleCase. "It is JSON like the other one" is not enough to go on. `GetLogEvents` must return BOTH `nextForwardToken` and `nextBackwardToken`: a client pages until the token stops changing, and a missing one reads as "start again". Writing to a group nobody created is refused, as CloudWatch refuses it, because a silently created group hides a typo and the lines end up nowhere anyone looks.
- **DynamoDB is a FOURTH dispatch rule.** The credential scope says `dynamodb` and the body is JSON 1.0, but the ACTION is a header: `X-Amz-Target: DynamoDB_20120810.PutItem`, posted to `/` like everything else. Routing on the credential scope alone answers every DynamoDB call identically.
- **Its `__type` is a FULLY QUALIFIED exception name** — `com.amazonaws.dynamodb.v20120810#ResourceNotFoundException` — and botocore keeps only what follows the `#`, so a bare code reads as the empty string and prints `An error occurred ()`. Every DynamoDB error is **400**, including "table not found".
- **A DynamoDB number is a decimal STRING on the wire because it does not fit a float.** Up to 38 significant digits; parsing one into a `float64` and printing it back is how `1e+06` appears where `1000000` was written. Nothing about an item is decoded and re-encoded — `{"S":"hi"}` is stored and returned exactly as it arrived — and the arithmetic in an update expression goes through `math/big`. Verified with a 30-digit value through `aws dynamodb put-item`/`get-item`.
- **An item's key is its type AND its value.** `{"N":"5"}` and `{"S":"5"}` are different keys, so any encoding that drops the type collides them. The key also comes from the table's own `KeySchema`, never from guessing which attributes look key-shaped.
- **An expression the emulator cannot parse must be REFUSED, not ignored.** The tempting failure is to treat an unparsed `FilterExpression` as matching everything, which turns an unimplemented filter into a silently wrong answer found nowhere near the cause. Nimbus answers `ValidationException` naming the construct (parentheses, `size()`, a nested path).
- **A key condition cannot be split on " AND "**, because `BETWEEN :lo AND :hi` contains one; and an update expression's clauses cannot be split on every comma, because `if_not_exists(a, :v)` does. The `ADD` inside an attribute named `ADDRESS` is not a verb either — match on word boundaries.
- **A table has its own read-back calls**, the DynamoDB version of S3's dozen bucket sub-resources: `ListTagsOfResource`, `DescribeContinuousBackups` and `DescribeTimeToLive` are all called straight after a create, and each needs its own "nothing is configured" document rather than an error. `BatchWriteItem` must always return `UnprocessedItems`, even empty, because a client reads the field before checking it.
- **A Query with an `IndexName` needs no separate storage.** A secondary index's keys are ordinary attributes of the same items, so the key condition selects on them and the sort key orders them. What is missing is the projection type, so an index query can return attributes a `KEYS_ONLY` index would omit — too much, which a client narrows itself.
- **`aws eks get-token` builds its bearer token entirely client-side** — a presigned STS URL, signed at the moment kubectl runs — so Nimbus never sees it being made and no static token file in k3s can ever match it. An API server handed a bearer token it cannot authenticate answers 401; it does NOT fall back to anonymous. The only mechanism that works is the one real EKS uses: a **token authentication webhook** (that is what aws-iam-authenticator is). k3s takes `--kube-apiserver-arg=--authentication-token-webhook-config-file=...`, and `/_nimbus/eks/token-review` answers `TokenReview` with `system:masters`. Measured: `kubectl get nodes` against a two-node cluster.
- **The webhook's kubeconfig must be bind-mounted, not written afterwards.** k3s reads its arguments at startup, so there is no moment between the container existing and the file being needed. And the webhook is called by the cluster's own API server, which signs nothing — so its path is routed *before* anything looks at a SigV4 credential scope.
- **A TokenReview response must echo the request's `apiVersion` and `kind`**, and the API server says nothing useful when it does not. The server address in the webhook kubeconfig is reached from inside the container, so it is `host.docker.internal`, which has been in the Nimbus certificate's SANs since Milestone 2.
- **REST-JSON errors must name the exception type TWICE**: the `x-amzn-ErrorType` header and the body's `__type`. Different SDK versions read different ones, and a client that finds neither raises a generic failure rather than the `ResourceNotFoundException` the provider is written to tolerate — so a destroy retries until it times out. This is EC2's "a describe must error with that kind's own code", one protocol over.
- **S3 is addressed path-style**, which is why AWS needs no TLS here: no `bucket.host` name means no certificate and no DNS. `s3_use_path_style = true` for the provider; the CLI needs `addressing_style = path`.

## GCP protocol facts (measured against the google provider 6.x)

- **The provider makes NO startup calls.** azurerm probes and waits ~20 s on a resource group; the aws provider reads three VPC attributes nobody asked about. Google goes straight to the resource it was told to create: a five-resource apply is fifteen requests, and a plan is one GET each. There is no surprise call to discover.
- **An operation that already says DONE is never polled.** Compute writes answer with an Operation object; the provider reads `status` out of the response it was handed and goes straight to reading the resource. The operations endpoint still has to exist — gcloud polls regardless, and an unknown id must 404 rather than be invented — but the fast path costs no second request. Operations are kept in memory, not in the store: six per apply would bury the five resources that were created.
- **Identity is a self link**, the full URL the resource answers on, and that is the store's ID. It embeds the port, so ids in a persisted state file are only valid for the port that wrote them — the same price Azure's storage suffix and ACR's loginServer pay for being addressable.
- **Numbers travel as decimal STRINGS**: `"id": "1234"`, `"size": "12"`, `"generation"`, `"projectNumber"`, `"metageneration"`. A client unmarshals them into string fields, so sending a JSON number lands as the zero value with nothing to point at.
- **A `*_custom_endpoint` carries its version for some services and not others.** `compute_custom_endpoint` and `storage_custom_endpoint` end in `/compute/v1/` and `/storage/v1/`; `iam_custom_endpoint` is the bare origin, because the provider appends `v1/projects/...` itself. Getting it wrong produces `/iam/v1/v1/projects/...`, which is how this was found.
- **A PATCH's `updateMask` is a whitelist, and Compute and IAM put it in different places** — Compute in the query string, IAM in the request body beside the object. Applying the whole body instead would silently clear every field the client left out.
- **A firewall rule's protocol field is `IPProtocol`**, with that capitalisation, inside `allowed[]`. A client reading `ipProtocol` finds nothing and plans a change on every run.
- **A subnetwork's `region` and `network` arrive as partial URLs and must come back as full self links**, and the network's own `subnetworks` list has to learn about the subnetwork — the provider reads that list off the PARENT on a later refresh. Same parent/child mirror as AKS node pools and Azure subnets, through `core.Store.Update` for the same reason.
- **Creating a service account costs ten seconds of client-side sleep.** The provider waits for IAM propagation after the create; nothing Nimbus returns shortens it, exactly like azurerm's twenty silent seconds on a resource group. Don't re-chase it.
- **Cloud Storage has three upload protocols and a client picks by size.** `uploadType=media` is bytes with the name in the query; `multipart` is a multipart/related body whose FIRST part is the metadata and whose second is the content, told apart by ORDER because the parts carry no names; `resumable` is a POST that answers with a session URI in `Location`, then PUTs with `Content-Range` where every incomplete chunk must answer **308** with an inclusive `Range: bytes=0-N`. A 200 too early and the client stops sending, leaving the object silently truncated.
- **`md5Hash` is base64 of the raw digest and `crc32c` is Castagnoli**, not the CRC-32 everything else uses, big-endian and base64. Both are digests GCS always reports — unlike Azure's `Content-MD5`, which is a content setting that must never be invented.
- **A bucket refuses to be deleted while it holds anything**, and `force_destroy` is the provider emptying it first: measured, it lists `GET /b/{b}/o?versions=true` before the delete. Deleting an OBJECT that is not there succeeds. Exactly S3's rule, one cloud later.
- **A 404 on `GET /b/{bucket}/anywhereCaches/` silently disables `force_destroy`.** The provider asks for Anywhere Caches *inside* its delete loop, and its own code breaks out of that loop when the call errors — so the 404 is never reported anywhere. It skips deleting the bucket's objects entirely and goes straight to deleting the bucket, which then fails on "the bucket is not empty" with nothing connecting the two. Measured against google 6.50.0: it listed the object, then deleted the bucket without ever trying to delete the object. Answer an empty `storage#anywhereCaches` list. This is the S3 sub-resource lesson in its most expensive form: it is not enough for an unimplemented sub-resource to fail *politely* — a client may be reading the failure as something else entirely.
- **`gcloud storage cp` quotes its multipart boundary with SINGLE quotes** — `multipart/related; boundary='===============15054...=='` — which RFC 2045 does not allow: a parameter value is a bare token or a double-quoted string. Go's `mime.ParseMediaType` refuses it outright with "mime: invalid media parameter", and the upload fails with an error that blames the request rather than the quoting. `boundaryOf` falls back to reading the parameter by hand and stripping a MATCHING pair of quotes — only matching, because a boundary legitimately ends in `==`. Same shape as `az deployment` splicing a template into a body and calling it JSON: the client is what it is.
- **`gcloud` asks for `GET /b/{bucket}/storageLayout` before it uploads**, to find out whether the bucket has a hierarchical namespace. A 404 does not stop the upload, but it puts a red line in the activity feed for something that is working.
- **`gcloud config set api_endpoint_overrides/...` warns about the "universe domain"** on every override — a newer gcloud concept that expects every endpoint to live under `googleapis.com`. The warnings are noise here and everything works through them; `--universe-domain` on the configuration is for real alternative universes, not for a local emulator.
- **An object name is a flat key that may contain slashes.** `img/logo.svg` is one object; splitting the path on `/` turns it into a 404. A `delimiter` in a listing collapses names into `prefixes[]`, which is how a client draws folders over a flat key space.
- **The API version belongs to the CLIENT, not to the service.** `compute` and `storage` carry `/v1/` in their endpoint; `iam`, `container` and `cloudresourcemanager` do not, because the client appends it. Worse, the two clients disagree about the SAME service: gcloud wants the bare origin for `pubsub`, while the provider wants `pubsub_custom_endpoint` to end in `/v1/`. A wrong guess produces `/v1/v1/projects/...`, which 404s naming the wrong API. Nimbus routes a path with the prefix, without it, and does not pretend there is a rule.
- **`gcloud run` prefixes the REGION onto the HOST**, because real Cloud Run is `us-central1-run.googleapis.com`. Pointed at an IP it tries to resolve `us-central1-127.0.0.1`. The override has to be a nested `*.localhost` NAME, which takes the prefix and still resolves to loopback — Milestone 2's DNS finding paying for itself two milestones later.
- **`gcloud run` does not speak the Cloud Run Admin API at all.** It uses the Knative serving API (`/apis/serving.knative.dev/v1/namespaces/{project}/services`), Kubernetes-shaped, where the Terraform provider uses `/v2/projects/{p}/locations/{l}/services`. Two wire formats for one resource in one product, with nothing announcing which a given tool uses.
- **GKE and Cloud Run poll OPPOSITE things, and getting it backwards is expensive.** GKE ignores its operation and polls the CLUSTER until `status` is RUNNING — four PROVISIONING reads in a row and it waited for all of them. Cloud Run ignores the service's own `terminalCondition` and polls the OPERATION — `done: true` was accepted instantly, and an operation without `done` was polled four times about ten seconds apart. So a GKE create answers at once and flips the status in the background, while a Cloud Run create must leave its operation unfinished until the container really answers. One way round gives a resource reported ready before anything is listening; the other gives an apply that waits for ever.
- **GKE is a different generated client inside the same provider.** Its user agent is `google-api-go-client/0.5`, every request carries `prettyPrint=false`, and its request bodies are WRAPPED — `{"cluster": {...}}`, `{"nodePool": {...}}`. Nothing else in GCP wraps, and a handler reading the body directly creates a resource with no name.
- **The same field name can have a different TYPE in two Google APIs.** An operation's `progress` is a number (0-100) in Compute and an object (`{name, metrics, stages}`) in the container API. Reusing Compute's shape failed the apply with `json: cannot unmarshal number into Go struct field Operation.progress of type container.OperationProgress`, which names neither GKE nor Nimbus.
- **A GKE node pool's `node_count` is not read — it is COMPUTED from the Compute API.** The provider's own comment says the container API does not report a count: it takes the pool's `instanceGroupUrls`, GETs each instance group manager and divides the summed `targetSize` by their number. A pool with no instance groups therefore reports ZERO, by division rather than by absence, and every plan wants to change the count to what it already is. Nothing in the diff mentions an instance group. Nimbus derives the manager from the pool rather than storing a second thing to keep in step. `gcloud container clusters list` reads NUM_NODES from the cluster's `currentNodeCount` instead — a third place for one number.
- **`remove_default_node_pool = true` deletes `default-pool` immediately after the create**, and almost every real GKE config sets it. A default pool that exists only as an entry in the cluster's `nodePools` array cannot be deleted, so the apply fails on a 404 for a pool Terraform was just told about. Real GKE's default pool is an ordinary node pool; so is this one.
- **A GKE cluster's `network` and `subnetwork` must come back in `networkConfig`**, not only in the top-level fields the create sent them in. Both are ForceNew, so with only the top-level ones filled a plan after a clean apply wanted to REPLACE the cluster.
- **The `endpoint` has to be filled by the CREATE, not when the cluster becomes RUNNING.** The provider writes state from a read taken while the cluster is still PROVISIONING and never looks again, so a late endpoint is empty in state for ever. Nothing is invented by doing it early: the host port is allocated synchronously, so the address is genuinely known before the container exists. The general rule is sharper than "derive, don't generate" — a derived value also has to exist by the time the client first reads it.
- **GKE's `setSize` is a COLON VERB on the pool's name** (`nodePools/workers:setSize`), not a path segment, like Pub/Sub's `:publish` and IAM's `:signJwt`. A Pub/Sub topic or subscription is created with **PUT on its own URL** rather than POST to a collection, and a Cloud Run service with **POST plus `?serviceId=`** and no name in the body. Three conventions for "create", one cloud.
- **The provider sends explicit JSON `null`s** for the policies a Pub/Sub config left out (`"retryPolicy": null`). Present-and-null is not absent, and anything reading a field has to survive both.
- **`gke-gcloud-auth-plugin` cannot work offline, and no webhook can save it.** It exists to exchange a Google OAuth credential for a Kubernetes token; under `auth/disable_credentials` there is none, so it produces nothing and nothing reaches Nimbus — unlike `aws eks get-token`, which builds a presigned URL offline and always sends something. It is not installed by default either, and `USE_GKE_GCLOUD_AUTH_PLUGIN=False` falls back to the in-tree `gcp` provider kubectl removed in 1.26. Nimbus supplies the client side instead: `nimbus gcp kubeconfig` writes one directly, and `nimbus gcp install-auth-plugin` drops a shim that answers the ExecCredential protocol, reading `KUBERNETES_EXEC_INFO` so it only answers for clusters on this machine.
- **A number set in Go is an `int`; the same number read back from JSON is a `float64`.** A helper that type-asserted only `float64` could not see a count written moments earlier in the same process, while the identical value round-tripped through the store worked perfectly — so every test passed and `gcloud` reported one node for a three-node cluster. Anything reading a number out of a `map[string]any` has to accept both.
- **A background goroutine that starts containers races the delete that stops them.** A node pool's rescale got past its "does this cluster exist" check, the cluster's delete stopped every container, and the rescale then started a fresh agent behind it: a `terraform destroy` that reported success, emptied the store, and left two k3s containers running. This is `core.Store.Update`'s lost update at the engine level — the check and the act have to be one step, under one lock.
- **Push delivery is the first thing Nimbus does OUTBOUND.** Everything else answers requests; a push subscription makes Nimbus an HTTP client against a URL that came out of a config. The endpoint is resolved and refused unless it is on this machine, retries are bounded, and every delivery is published to the bus — so the feed shows publish, push and the service's own request as one chain.

## The engines

Anything that really runs lives in `internal/engines`, shared by every cloud and knowing about none of them:

- `docker` — the container client (`Client`, with a `Fake` for tests), plus container naming, labels and free-port finding.
- `run` — HTTP services: pull an image, publish a port, wait for it to answer, proxy any method and path through to it. Behind Cloud Run. NOT `funcs` with a new name: a service answers arbitrary requests, is its own image with nothing mounted, and has no `X-Amz-Function-Error`.
- `k3s` — managed Kubernetes. One `Engine` per cloud (own name prefix, own registry of what it started) with `Start`, `ScaleAgents`, `WaitForNodes`, `Stop`, `Reattach`, `APIClient`, `MirrorRegistry` and `Watch`. The watcher mirrors pods into the store as `Nimbus.Kubernetes/*` with the engine's cloud on them, which is why the visualizer's Kubernetes view works for AKS and EKS alike with no new code.

The k3s engine now serves three clouds (AKS, EKS, GKE) unchanged. A cloud plugin supplies the resource id, the node count and a container name prefix; it keeps its own hooks, API shapes and bookkeeping. If you find yourself adding a cloud's vocabulary to an engine, it belongs in the plugin instead.

## Host and platform facts (the machine, not a cloud)

These are about the host Nimbus runs on, so they bite every cloud at once and
only ever show up on a machine you are not using.

- **`host.docker.internal` is a Docker DESKTOP convenience and does not exist on Docker Engine.** Nimbus writes it into a Lambda's `AWS_ENDPOINT_URL` and into the k3s token-webhook kubeconfig, and on Linux it resolves only with `--add-host host.docker.internal:host-gateway` — which `docker.runArgs` now passes on **every** container, unconditionally, because a per-cloud opt-in is exactly what was forgotten. The signature is a **401 from a cluster you just created**: `kubectl` says "You must be logged in to the server", not a connection error, because the API server is up and could not reach the webhook to review the token. AKS passed throughout while EKS and GKE failed, which is the discriminator — Azure authenticates with k3s's own kubeconfig and never calls back out. Nimbus binds `:port` rather than loopback, so the bridge gateway reaches it; needs Docker 20.10+ for `host-gateway`. Verified on Docker Desktop 29.9.2 that the override still reaches the host, so it is not a Linux-only flag with a macOS cost.
- **A name that will become a path must be judged as a NAME, not handed to `filepath`.** The two hosts disagree in both directions: `/absolute.py` is absolute on Unix and `filepath.IsAbs` is **false** for it on Windows, which needs a volume name — so a `filepath.IsAbs` guard let it through there; `C:/x` is the mirror image, absolute on Windows and an ordinary name containing a colon on Unix; and a backslash is a separator on Windows only, so `a\..\..\x` is one harmless segment to a `/`-split check and three levels up to `filepath.Join`. `funcs.safeJoin` and S3's `cleanKey` both judge the raw, slash-separated name now, so the same zip or key is refused on every machine. A drive letter is one letter, a colon, then end-of-segment — narrow on purpose, because a colon elsewhere is legal in a key and a timestamp has two.
- **Windows has no executable bit.** A file mode there drives only the read-only flag, so an unpacked `bootstrap` comes out `-rw-rw-rw-` however it was written. Nothing is lost — the bit matters inside the Linux container that runs the handler — but an assertion about it has to be skipped on Windows rather than weakened everywhere.
- **Windows's `filepath.IsAbs` and its missing executable bit are why the Windows CI leg exists.** It is the only leg that is not Linux or macOS, and both of the above were invisible on the other two.
- **aws-cli v1 and v2 have NO common inline `--payload`.** v2 reads one as base64 and fails with `Invalid base64: "{"id":...`, wanting `--cli-binary-format raw-in-base64-out`; v1 — what this project was measured against — takes the JSON raw and rejects that flag outright as `Unknown options`. Measured both ways. `--payload fileb://file` means "these bytes, verbatim" to both, so it is the only portable spelling, and it is what CI and the example use.
- **A CI job added in a close-out and never looked at can be red for three milestones.** The two AWS Docker jobs went in with M8 and had never once passed; the GKE job failed on its first run. All of it was the `host.docker.internal` gap, invisible on the Mac everything was proven on. Reading `gh run list` is part of closing out a milestone, not an optional extra.

## How a request flows (AWS)

1. `internal/aws/server.go` `ServeHTTP` records the request on the bus and routes it.
2. `internal/aws/sigv4.go` `serviceOf` reads the SigV4 credential scope — **the path says nothing**, every Query service posts to `/`.
3. The service's own file handles it: `sts.go`, `ec2.go` (+ `ec2_vpc.go`, `ec2_routing.go`, `ec2_sg.go`), `s3.go` (+ `s3_object.go`, `s3store.go`), `iam.go` (+ `iam_xml.go`).
4. Resources go into the same `core.Store` with `Cloud: "aws"`, an ARN or prefixed id as the ID, and the parent set so the graph nests them — a subnet's `ParentID` is its VPC, which is all the visualizer needs.

## Adding a resource type (the usual task)

1. Write a failing test in `internal/azure/*_test.go` that replays the client's calls (copy the shape from the SDK or a Terraform debug log: `TF_LOG=DEBUG terraform apply`).
2. Add a hook file (e.g. `storage.go`) and register it in `New()`.
3. Fill server-generated fields in `BeforePut`; start or stop a real engine in `AfterPut`/`AfterDelete` and set `Backing: "real"` if one runs.
4. Add a badge/colour for the type in `internal/ui/static/types-azure.js` (`TYPES`). `TestEverySpecTypeHasABadge` fails until you do.
5. Prove it with Terraform: add it to an example under `examples/terraform/` and apply + destroy.

## Changing the visualizer

- **It is multi-cloud.** Presentation is dispatched on each resource's own `cloud`: badges, colours, sibling order, which type is the root container, which types are addressing-only, and any non-containment links all come from that cloud's table (`types-azure.js`, `types-aws.js`) through `types.js`. A shared module must never key on a type name — `test/ui/clouds.test.js` fails the build if one does. A module that IS cloud-specific says so in its filename (`inspector-azure.js`) or is declared as that cloud's view in `render.js`'s `VIEWS`.
- The cloud tabs come from `/api/info`, which lists what `--clouds` started. Nothing is greyed out pretending to be coming later.
- Modules live in `internal/ui/static`, tests in `test/ui` (`node --test 'test/ui/*.test.js'` -- a glob, not a directory: node 24 tries to load a directory argument as a module). Keep the pure parts — models, layouts, matching — out of the DOM so they can be tested there.
- `?fixture` renders `static/fixture.json` with no server. Anything new that draws should be exercised by the fixture, so it can be looked at as well as asserted about.
- Rebuild (`go build -o bin/nimbus ./cmd/nimbus`) and restart before checking a change in the browser: the files are embedded.

## Milestone workflow (every session)

Each milestone has a prompt in `docs/prompts/`. When asked to work on one:

1. **Plan first.** Read the prompt, this file and `docs/ROADMAP.md`. Inspect the code it touches. Present a short plan (files, tests, open questions) and wait for approval before editing.
2. **Ask, don't guess, on decisions marked "ask the owner".** Give 2–3 options with a recommendation.
3. **Test first.** For every client call you support, add a test that replays it before implementing.
4. **Prove it with the real client** (Terraform, `az`, `kubectl`, `aws`, `gcloud`) on the owner's machine. The owner runs commands that need their machine (Docker, trusting certs, installing tools); tell them exactly what to run and what output to paste back.
5. **Stop at the done-criteria.** Do not start the next milestone. Note follow-ups in `docs/ROADMAP.md` under "Later".
6. **Close out:** all checks pass (`gofmt -l .`, `go vet ./...`, `go test ./...`); add any new protocol facts to the list above; mark the milestone done in `docs/ROADMAP.md` and move "Current" to the next one; write a short entry in `docs/CHANGELOG.md`; commit with a clear message.
7. **Then read CI** (`gh run list`, `gh run view --log-failed`) on the pushed commit, and fix what is red before calling the milestone finished. Local green is not CI green: the Linux runners have no Docker Desktop and the Windows leg has neither Unix path rules nor an executable bit. Any job added in this milestone has never run before — check it specifically, and check that a job added in an EARLIER one has actually been passing, because a job nobody looks at stays red.

If a session runs long, stop at a green, committed checkpoint and write what is left at the top of `docs/ROADMAP.md`, so the next session can resume from it.
